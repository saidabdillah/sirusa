# Admin

## Access control = menu grants, NOT role route groups
All route-level `role:*` middleware groups were removed. `routes/web.php` wraps everything after login in `['auth','status.aktif','akses.menu']`. Granting/revoking access is done purely by checking menus on the "Kelola Akses → Akses Menu" page (`Admin\MenuController`), whose matrix is `roles × menus` (pivot `role_menu`); separate from that, the "Kelola Menu" page (`admin.menuKelola.*`) adds/edits/deletes the menu entries themselves. Middleware `EnsureMenuAccess` (alias `akses.menu`) 403s any request whose route is covered by a menu that `User::hasMenuAccess()` denies; routes not covered by any menu pass through. `User` model exposes `menus()`, `menuScopes()`, `hasMenuAccess($scope)`, and static `menuScopeCovers($scope, $routeName)` (a menu scope covers its exact route name AND every route prefixed by `scope . '.'`). Views hide/disable action areas with `hasMenuAccess('admin.X.index')`. Default `MenuSeeder` grants:
- `super_admin` = dasbor + everything (beasiswa, pendaftar, all three verifikasi leaves, kampus, and the whole Kelola Akses group: Role, Pengguna, Akses Menu, Kelola Menu);
- `capil` = dasbor + `admin.capil`;
- `kampus` = dasbor + `admin.kampusverif` (NO `admin.kampus` — the Kampus Master Data page belongs to kesra, NOT the kampus role);
- `kesra` = dasbor + `admin.beasiswa` + `admin.pendaftar` + `admin.kesra` + `admin.kampus` (Master Data → Kampus is managed by kesra) + `admin.pengguna` — the last one needs its PARENT `kelola-akses` granted too, because `sidebarMenus()` only selects `parent_id` null menus, so without the parent the "Pengguna" item never appears in the sidebar (parents have `scope = null`, so the grant gives visibility only, never route access — look them up by `Str::kebab(label)` in seeders, not by `scope`);
- `user` = dasbor + `user.beasiswa` + `user.pendaftaran`.

`MenuSeeder` groups: **Kelola Akses** (children Role/`admin.role`, Pengguna/`admin.pengguna`, Akses Menu/`admin.menu`, Kelola Menu/`admin.menuKelola`) and **Master Data** (children = Kampus only — Pengguna was moved OUT of Master Data into Kelola Akses). **Verifikasi is NOT a dropdown anymore**: it is three TOP-LEVEL leaf menus `Verifikasi Capil` (`fas fa-id-card`, urutan 25), `Verifikasi Kampus` (`fas fa-graduation-cap`, urutan 26), `Verifikasi Kesra` (`fas fa-clipboard-check`, urutan 27) emitted directly by `MenuSeeder` on a fresh seed (the old flatten migration `2026_09_25_110300_restructure_verifikasi_menus` was DELETED).

There is NO generic `admin` role anymore — always use the specific `capil`/`kampus`/`kesra`. `dashboard` menu is `wajib` (`RoleController::store` auto-grants it); the grant matrix force-keeps `wajib` menus and, for `super_admin`, also `['admin.role','admin.menu','admin.menuKelola','admin.pengguna']` (`MenuController::superAdminModuleIds`).

## Canonical roles (exactly five — short names, NOT `admin_*`)
The `roles` table MUST contain exactly `super_admin`, `capil`, `kampus`, `kesra`, `user` — created directly with these short names by `DatabaseSeeder`/`seedAkses()`; the historical `2026_09_25` `standardize_roles`/`rename_admin_roles_to_short_names` migrations were DELETED (the app is unpublished: schema changes are edited in-place into the create migrations, never new ALTER TABLE migrations). Treat `capil`/`kampus`/`kesra` as the ONLY canonical admin role names — never create legacy `admin_*` or old-style short duplicates. The same three strings double as verification STAGE keys (`UserProfile::verifStages()` → `verif_capil`/`verif_kampus`/`verif_kesra`, `VerifikasiController::STAGES`) — the role/scope/route namespaces `admin.capil.*`/`admin.kampusverif.*`/`admin.kesra.*` stay unchanged. `DatabaseSeeder`, Pest `seedAkses()`, and `UserFactory` (`admin()`→kesra, `capil()`→capil, `kampusAdmin()`→kampus) all seed/assign the short names; keep them in sync (also with `UpdateUserRequest` `in:` whitelist and the peran dropdowns/$roleLabels). Known quirk: `MenuSeeder` inserts `role_menu` with plain `DB::table('role_menu')->insert` (not `insertOrIgnore`) — re-running it on an existing DB duplicates grant rows, so do NOT re-seed MenuSeeder over an existing DB.

## super_admin semantic checks that REMAIN (do not remove)
Menu grants cover azimuth; a few hard rules still use `hasRole` because they protect the super_admin account itself:
- `PenggunaController`: the MODULE (index/create/store/edit/update) is gated on `User::canManageUsers()` = `hasMenuAccess('admin.pengguna.index')`, NOT `hasRole` — `MenuSeeder` grants `kelola-akses` + `admin.pengguna` to `kesra`, so superadmin and kesra both manage users out of the box and superadmin can widen it from Akses Menu. `destroy`, `resetPassword` and `toggleStatus` remain `hasRole('super_admin')` (credentials + the super_admin account itself), each with an explicit `abort_unless`; `toggleStatus` refuses any `super_admin` target, which also stops a super_admin disabling themselves. `abortUnlessMayTouch()` (GET form) and `UpdateUserRequest::authorize()` (PUT) both 403 a non-super_admin touching a super_admin target. Destroy blocks deleting self and deleting other super_admins. `resetPassword` (POST `admin.pengguna.reset-password`) sets the account back to password `12345678`.
- `StoreUserRequest`/`UpdateUserRequest` `authorize()` require `canManageUsers()`; `UpdateRoleRequest` + `RoleController::destroy` block touching the `super_admin` role (no manage/delete UI for super_admin).
Views `admin/pengguna/{index,buat,ubah}` conditionally show those actions: Ubah follows `canManageUsers()`, while Nonaktifkan–Aktifkan / Reset Password / Hapus User follow `hasRole('super_admin')`. On the Pengguna index the actions live in a dropdown button-group (the "Ubah Role" label is just **Ubah**), each backed by its own form and per-page `@push('script')` Swal confirm handler (`.btn-confirm-toggle` for toggle+reset, `.btn-delete` for hapus). The `admin/pengguna/ubah` form contains NO email display and NO password fields — password changes are NOT possible there (only the index's Reset Password quick action resets to `12345678`). The super_admin row has no action buttons at all; a kesra row only gets the Ubah link.

## User management identity rules (create/edit)
`peran` in BOTH requests is `required` + `Rule::in($this->user()->assignableRoles())` — see `.ai/rules/user.md` for why it is neither `Rule::exists('roles','name')` nor `nullable`. `username` uses `required_unless:peran,user` (required for non-user peran, unique) but auto-generated (`usr` + Str::random(8)) for `user` peran. Do NOT write `required_if:peran,!user` — Laravel does not support `!` negation in string dependent rules (it only matches the literal string `!user`), use `required_unless` instead (error message tasks ask for "Username wajib diisi untuk akun non-mahasiswa"). `email` is nullable/OPTIONAL (the buat form shows NO `*` on Email); `password`+`password_confirmation` required unless peran = user (initial password = `12345678`); `nik` `required_if:peran,user` ONLY (non-user roles submit no NIK — `required_unless:peran,super_admin` was a bug that forced NIK on every staff account), unique on `profil_pengguna`; there is NO `nim` rule (mahasiswa set it on the Profil page); `kampus_id` uses `Rule::requiredIf($this->input('peran') === 'kampus')` (the label carries `*`) + `exists:kampus,id`. `PenggunaController::store` sets password to `12345678` when peran = user and seeds `profile()->create(['nik' => $validated['nik']])`, and its success flash mentions the initial password only for the mahasiswa branch. `UpdateUserRequest` applies the SAME `kampus_id` `Rule::requiredIf(peran === 'kampus')`. It has NO `password`, `nik`, or `nim` rules — the edit ("Ubah") form only changes peran and status (username/email/password/NIK/NIM are fixed after creation); password resets go through the dedicated `admin.pengguna.reset-password` action only. `PenggunaController::update` updates only `status`/`kampus_id` explicitly and calls `syncRoles($validated['peran'])` — never pass `peran` to `update()`, it is not fillable.

## Pengguna create/edit views toggle field blocks by peran
`admin/pengguna/buat` shows/hides three blocks via a jQuery `toggleAkun()` on `#peran` change: `#akunMahasiswa` (NIK, visible only for peran `user` — note the staff password block is `#akunStaf` and must show when NOT user: the old vanilla-JS version had `akunStaf.classList.toggle('d-none', !isUser)` which INVERTED it so password fields appeared for mahasiswa and vanished for admins), `#akunStaf` (Kata Sandi + Konfirmasi, hidden for peran `user`), `#akunKampus` (kampus select, only peran `kampus`), and the username field wrapper `[data-field="username"]` (hidden for peran `user` — auto-generated). `admin/pengguna/ubah` renders ONLY Username (readonly), Peran (`old('peran', $user->roles->first()?->name)` fallback — no preselected default), Status, and the `#akunKampus` select; NO NIK inputs and NO password fields (test asserts `assertDontSee('name="nik"')` and `Konfirmasi Kata Sandi`); email/NIK show as read-only text in the right-hand Informasi card.

## Beasiswa, kampus, pendaftar: single admin group
There is no super_admin/admin role split for scholarship, kampus, or pendaftar routes anymore — access follows the menu grant (`admin.beasiswa`, `admin.kampus`, `admin.pendaftar`). Form Requests for those modules `authorize()` with `return true;` — the `akses.menu` middleware is the only guard. Buttons in `admin/beasiswa/{index,lihat}`, `admin/kampus/*`, `admin/pendaftar/index` gate on `hasMenuAccess('admin.beasiswa.index'|'admin.kampus.index'|'admin.pendaftar.index')`. Since super_admin and kesra are granted everything by default, both CAN manage beasiswa/pendaftar (intended; the old "super_admin is view-only" rule is obsolete).

## Scholarship form uses the local kampus catalog
The admin beasiswa create/edit form selects one `kampus_id` from the local `kampus` table (checkbox tree of catalog fakultas→prodi posting `prodi_ids[]`). Store/UpdateScholarshipRequest validate `kampus_id` + `prodi_ids` and use `after()` to reject prodi whose fakultas.kampus_id != selected kampus. Store/update resolve the kampus name into the legacy `beasiswa.kampus` text column and rebuild snapshot rows via `syncFakultas()`. Only store() notifies all role('user') with NewScholarship (database). Tables `kampus→fakultas→prodi` live in migration `2026_08_24_000001_create_kampus_table.php` (edited in place; project runs `migrate:fresh --seed`, do NOT create new migration files). The scholarship form has NO "Tunjangan" (`cakupan`) field and uses two flatpickr date inputs `tanggal_mulai`/`tanggal_selesai` instead of the old single `batas_waktu` (see `views.md` → "Beasiswa periode & UKT cleave").

## Profile verification stages (capil → kampus → kesra)
`Admin\VerifikasiController` drives profil verification. Routes `admin.capil.*`, `admin.kampusverif.*`, `admin.kesra.*` use `->defaults('stage', ...)` and a bound `{user}`. CRITICAL dispatcher gotcha: Laravel aligns controller params POSITIONALLY against `array_values($route->parameters())`, which orders the bound `{user}` model before the `stage` default — so method signatures MUST be `(User $user, string $stage, ...)` (User first, then stage, then FormRequest). Stage order and mapping live in `UserProfile::verifStages()` (`capil/kampus/kesra` → `verif_*`/`catatan_*` columns). `canVerifStage($stage)` is false when already verified, stage already setuju, or any previous stage is not setuju. `verifikasi` action sets `{$verif}=status` + `{$catatan}=catatan`, notifies `DataVerificationChanged`, and redirects to the stage index. Keputusan is `setuju|revisi|tolak` (see `VerifikasiProfilRequest`); `tolak` acts like `revisi` for sequencing (downstream stages blocked until the profile is saved again). `UserProfile::verifStatus()` returns `revisi` if any stage is `revisi`, else `tolak` if any is `tolak`, else `proses`. Index queries `User::role('user')->where('status','aktif')` filtered by `canVerifStage`. Profile save (ProfileController) calls `resetVerification()` which resets all stages to `menunggu` and clears catatan — the profile must be re-verified after any edit.

## Roles & menus management
`Admin\RoleController`: index lists roles WITHOUT user-count/menu-count columns; store/create auto-grants `wajib` menus; update; destroy refuses `super_admin` and any role still holding users. There are NO `create`/`edit` page methods — Tambah/Ubah run through modals on the index page (routes `admin.role.simpan`/`perbarui` only; `role.buat`/`role.ubah` GET routes no longer exist). `Admin\MenuController` splits into TWO areas:
- **Akses Menu** (`/menu`, scope `admin.menu`): `index` renders the roles × menus matrix as a COLLAPSIBLE TREE (`Menu::with('children')`, grants from `role_menu`) — parent rows toggle `data-tree-child-of` rows, so only the subtree of an open parent is visible; no CRUD, no "Tambah" button. `perbarui` (PUT `/menu`, route name `admin.menu.grants` — the only alias under `admin.menu` besides `index`) syncs `role_menu` from `grants.*.*`, force-adds `wajib` menus, and force-keeps `superAdminModuleIds` (`['admin.role','admin.menu','admin.menuKelola','admin.pengguna']`) on super_admin.
- **Kelola Menu** (`/menu/kelola`, scope **`admin.menuKelola`**, routes `admin.menuKelola.index/simpan/perbarui/hapus` — NO `buat`/`ubah` GET routes): the index renders the tree list and all add/edit happen via Bootstrap MODALS (partials `admin.menu.modal-tambah` + per-menu `admin.menu.modal-ubah`; `kelola()` passes `$menus`, `$parents` (top-level for the parent select), `$sections`). THE MODALS MUST BE RENDERED AT `<body>` LEVEL, NOT inside `.main-content`/`.main-wrapper`: those ancestors form a stacking context so `position:fixed` modals land UNDER the backdrop (symptom: "modal seperti di belakang"). Pattern: pages emit them inside `@push('modal')`, the layout outputs `@stack('modal')` right before `</body>` (after `@stack('script')`); variable scope stays intact because `@push` blocks evaluate where they're written, still inside `@section('content')`. Naming gotcha — these routes MUST NOT be prefixed `admin.menu.`, because `menuScopeCovers('admin.menu', $routeName)` covers every `admin.menu.*` route; the `admin.menuKelola.*` namespace avoids the prefix collision. Modal forms carry a hidden `modal_target` (e.g. `modal-tambah-menu`, `modal-ubah-menu-{id}`) and on validation failure redirect back to the index where JS reopens `old('modal_target')` with `$('#id').modal('show')`; every `old()`/`$errors` render in a modal is gated by `$isTarget = old('modal_target') === <that modal's id>` so a failed submit only re-fills/reopens the modal that was submitted. `store` auto-grants the new menu to `super_admin`; `destroy` refuses `wajib` menus and menus that still have children. `Menu::sections()` is the section whitelist. `StoreMenuRequest`/`UpdateMenuRequest` require a REGISTERED route (`Route::has`) or a `scope` (`regex /^[a-z][a-z0-9._-]*$/`) for every leaf — enforced in `withValidator()->after()` (NOT as a closure rule, because `nullable` short-circuits closures when the value is null). Update rejects `parent_id` equal to the menu's own id. All routes under `admin.menu` and `admin.menuKelola` are granted only to `super_admin`, so non-super_admins get 403.

## Admin list views use server-side DataTables
Kampus (kampus/fakultas/prodi), beasiswa, and pendaftar index pages are server-side DataTables (Stisla `datatables.min.js`): the tbody is still hydrated inline (so existing `KampusManagementTest`/`PendaftarFilterTest` keep passing) and each table re-requests its JSON endpoint via `ajax: { url: route('admin.X.data') }` with `serverSide: true`. One GET endpoint per table lives in the controller (`data(Request)`), behind a `admin.X.data` route registered inside the same menu-gated group (covered → 403 by `EnsureMenuAccess`). All JSON is produced by `App\Support\DataTablesProcessor`: ctor `(Request $request, Builder|Relation $query, array $config, Closure $rowBuilder)`. `$config` keys: `searchable` (strings or `fn($q,$term)=>` closure, run inside one `where(...)` group), `orderable` (`columnIndex => dbCol`), and optional `filter` (`fn(Builder $query, Request $request)`) executed AFTER `recordsTotal` but BEFORE `recordsFiltered` — NEVER pre-filter the query in the controller before constructing the processor or `recordsTotal` will reflect the filter. Row cells are built in PHP, single-sourced through the same `_aksi` partial the inline tbody uses; `aksi`/`checkbox` cells are gated by `hasMenuAccess('admin.X.index')` so empty rows stay column-complete. EXCEPTION: the **pendaftar** table is fully READ-ONLY — it has no aksi/checkbox cell at all (its old `_aksi` partial and `admin.pendaftar.lihat` route were deleted; `data()` returns no `aksi` key and the DataTable `columns`/`columnDefs` end at the `status` column, target `[0]`). Index pages keep a `->limit(25)->get()` tbody (first page) while `data()` serves full pagination (length `-1` capped at 100). Do not add Tailwind/Bootstrap 5 — STISLA + Bootstrap 4 only. The pendaftar index filter (`status` + `beasiswa_id`) submits via a GET "Cari" button (`type="submit"`), NOT `onchange="this.form.submit()"` — the selects must never auto-submit; keep a separate Reset link.

## Demo seed users (database/seeders/UserSeeder.php)
`UserSeeder` creates demo users (emails `user01@`.., usernames `user01`.., plus `penerima01`.. for filled recipients) each with peran `user`, status `aktif`, fully-populated `profil_pengguna` (unique `nik`/`nim`, `nim` >= 8), and **password = `12345678`**. `DatabaseSeeder` seeds the roles `super_admin`/`capil`/`kampus`/`kesra`/`user` and demo accounts `superadmin`, `kesra` (kesra@sirusa.com), `kampus` (kampus@sirusa.com), `capil` (capil@sirusa.com) — all password `12345678` — then calls KampusSeeder, ScholarshipSeeder, UserSeeder, and MenuSeeder. The default super_admin login is by username; user logins are by NIK.

## Sidebar (Stisla) is dynamic
`resources/views/layouts/partials/sidebar.blade.php` renders sections in order from `Menu::sections()` (`['Menu Utama','Menu Admin','Menu Pengguna','Pengaturan','Manajemen']`). It iterates `$user->sidebarMenus()` — a `User` helper returning ONLY top-level menus (`whereNull('parent_id')`, `aktif`, granted to the role) with already-filtered ordered `children` (granted + `aktif`, sorted by `urutan`). Do NOT switch back to `$user->menus()`: it returns every granted menu including children, and rendering children as top-level items was the old "double menu" sidebar bug. Leaf links call `route($menu->route)` guarded by `\Illuminate\Support\Facades\Route::has($menu->route)` — an unregistered/stale route renders a dead `<span>` instead of crashing (submit zero-length menu pages). Parent dropdowns render only when `children` is non-empty. Parent `li` gets `active` when any granted child route is current so the submenu stays open.

## Pengguna module: menu grant for breadth, hasRole only to guard super_admin
Index/create/store/edit/update are gated on `User::canManageUsers()` (= `hasMenuAccess('admin.pengguna.index')`), so the Akses Menu matrix — not a hardcoded role list — decides who may open the module; `MenuSeeder` grants `kelola-akses` + `admin.pengguna` to kesra (the parent grant is what makes the item appear in the sidebar, since `sidebarMenus()` only selects `parent_id` null menus). Delete, reset-password and toggle-status stay `hasRole('super_admin')` because they guard credentials and the super_admin account itself. `abortUnlessMayTouch()` / `UpdateUserRequest::authorize()` 403 any non-super_admin touching a super_admin target, so the GET form and the PUT fail the same way.

## update() guards the actor's own account and super_admin targets
`update()` returns a redirect + `error` flash (never an exception) when the actor changes their own `peran` or sets their own `status` to `non-aktif`, and when a `super_admin` target's `peran` is changed or its `status` is set to `non-aktif` — the form was previously able to demote and deactivate super_admins, which `destroy()`/`toggleStatus()` already refused. `toggleStatus()` now has an explicit `abort_unless(hasRole('super_admin'))` (it used to rely on the menu grant for its 403, so it broke the moment kesra got the grant) and refuses any `super_admin` target, which also stops a super_admin disabling themselves.

## Changing a verification decision cascades to later stages
In `verifikasi()`, whenever the submitted status is not `setuju`, call `resetDownstreamStages($stage)` before saving. Prerequisites are now re-editable, so leaving a stale `setuju` downstream would let a student skip straight to Kesra after Capil rejected them. `VerifikasiProfilRequest` also accepts `menunggu` (Tarik Kembali) for this reason.
