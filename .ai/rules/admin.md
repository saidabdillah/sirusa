# Admin

## Role authorization for admin user management
User management (PenggunaController) splits capabilities by role: both super_admin and admin can index users and toggle status; only super_admin can create, edit, delete users, or change roles. destroy() blocks deleting self and deleting other super_admins; toggleStatus blocks non-super_admin toggling a super_admin. Store/UpdateUserRequest authorize only super_admin; UpdateUserRequest marks 'peran' nullable (non-super admins never send it). Admin view (admin/pengguna/index) conditionally shows buttons per role.

## Scholarship role split
Scholarship (BeasiswaController) routes are split: index & lihat in a `role:super_admin|admin` group; create/store/edit/update/destroy in a `role:admin` group (routes/web.php). Store/UpdateScholarshipRequest authorize only via `hasRole('admin')`. super_admin is limited to viewing index+detail (no action buttons — views admin/beasiswa/{index,lihat} wrap actions in `@if(hasRole('admin'))`).

## Scholarship form uses the local kampus catalog
The admin beasiswa create/edit form no longer uses the external select2 kampus API. It selects one `kampus_id` from the local `kampus` table (view shows a checkbox tree of catalog fakultas→prodi posting `prodi_ids[]`). Store/UpdateScholarshipRequest validate `kampus_id` (exists:kampus,id) + `prodi_ids` (array, min 1, each exists:prodi,id) and use `after()` to reject prodi whose fakultas.kampus_id != selected kampus. BeasiswaController::store/update resolve `kampus.nama_kampus` into the legacy `beasiswa.kampus` text column and rebuild snapshot rows in `beasiswa_fakultas`/`beasiswa_prodi` (copies of catalog names, no FK to catalog) via `syncFakultas()`. Only store() notifies all role('user') with NewScholarship (mail+database); edit/update/destroy never notify. Tables `kampus→fakultas→prodi` live in the single migration `2026_08_24_000001_create_kampus_table.php` (edited in place; this project runs `migrate:fresh --seed`, do NOT create new migration files per user preference). `BeasiswaController::edit()` computes `$selectedKampusId` = `scholarship.kampus_id`, falling back to the first catalog kampus whose prodi names intersect the snapshot prodi names when `kampus_id` is null (covers factory/legacy beasiswa); the edit view selects that kampus and the JS tree shows the matching prodi as checked (matches snapshots by prodi name).

## Applicant role split
Applicant (PendaftarController) routes: index/lihat in `role:super_admin|admin` (both can view); perbarui (PUT status) and destroy (DELETE) in the `role:admin` group only (routes/web.php). So only admin verifies (changes status) and deletes applicants; super_admin is view-only (index/detail, no form/card — admin/pendaftar/lihat hides the "Ubah Status" and "Aksi" cards for non-admin). update() always filters validated data to only `status`+`catatan` keys.

## Announcement page (accepted = directly awarded)
Admin setting status `diterima` directly awards the scholarship (`UpdateApplicantRequest` enforces quota: rejecting `diterima` when full; rejected from `ditolak`, only from `verifikasi`/`revisi`).

Public `pengumuman.show` page (`User\PengumumanController::show`, route in the authenticated `['auth','status.aktif']` group, NOT role-restricted so admins+users can view) lists the accepted applicants of a scholarship. It is governed by a date window on the `beasiswa` table: `tanggal_pengumuman` (start) + `tanggal_pengumuman_selesai` (end) + `pengumuman_notified_at` (guard for scheduler). Halaman tampil otomatis saat `isPengumumanAktif()` true DAN ada minimal 1 penerima (`hasPengumuman()`); otherwise `abort(404)`. The sidebar (user role) lists active-announcement scholarships dynamically. The announcement window dates are NEVER set from the beasiswa create/edit form (the buat/ubah form has no announcement inputs); they are managed ONLY via the dedicated schedule page (see below).

## Announcement schedule management (separate admin page) + exports
A dedicated admin page manages the announcement window per scholarship WITHOUT restructuring the DB (data stays in the `beasiswa` columns). `Admin\PengumumanJadwalController` index is in the `role:super_admin|admin` group (both can view); edit/update/destroy are in the `role:admin` group. `UpdatePengumumanRequest` authorizes only `admin`, allows both dates nullable, requires them set together, and rejects selesai < mulai (uses the typed `Validator $validator` closure in `after()`, same convention as `UpdateScholarshipRequest`). It ALSO rejects `tanggal_pengumuman` <= the scholarship's `batas_waktu` (the "mulai after batas_waktu" rule that used to live in `StoreScholarshipRequest`, now enforced only on the schedule page). update() and destroy() both reset `pengumuman_notified_at` to null so the scheduler re-notifies on a fresh window; "delete announcement" = null both date columns (keeps the scholarship). Views: `admin/pengumuman/{index,ubah}`; sidebar "Pengumuman" is grouped inside the "Beasiswa" dropdown under both super_admin+admin. The `admin/pengumuman/ubah` error blocks (`@error('tanggal_pengumuman')`/`@error('tanggal_pengumuman_selesai')`) MUST use `invalid-feedback d-block` (not plain `invalid-feedback`) because the inputs live inside `.input-group`, which breaks Bootstrap's `.form-control.is-invalid ~ .invalid-feedback` sibling selector so the message would otherwise never render.

Exports:
- Excel daftar pendaftar: `App\Exports\PendaftarExport` (maatwebsite/excel v4, `FromQuery`+`WithHeadings`+`WithMapping`+`ShouldAutoSize`), the `admin.pendaftar.export` GET route (in `role:super_admin|admin`, must be declared BEFORE `admin/pendaftar/{applicant}/lihat` to avoid binding conflict) reuses the same status/beasiswa_id filters as the index; button on `admin/pendaftar/index` passes `request()->only(['status','beasiswa_id'])`. Export rows include the full profile: identity (tempat/tanggal lahir, jenis kelamin, agama, alamat, provinsi/kabkota/kecamatan/desa), `status_orang_tua`, and ayah/ibu/wali blocks (nama, status/hubungan, pekerjaan, penghasilan, NIK) — values read from `user.profile` (already eager-loaded in `query()`), `?? '-'`; `ScholarshipSeeder` links every beasiswa to a catalog `kampus_id` so seeded beasiswa are editable.
- PDF penerima: `User\PengumumanController::exportPdf` (barryvdh/laravel-dompdf) route `admin.pengumuman.export-pdf` in `role:super_admin|admin`; `abort(403)` unless user has admin/super_admin role, `abort(404)` when no penerima; renders `admin/exports/penerima_pdf`. Buttons on `admin/beasiswa/lihat` (Pengumuman card).

## User apply flow auto-fills from profile
`StoreApplicantRequest` accepts only `beasiswa_id` + 9 dokumen; faculty/prodi/ipk/semester are derived from `user->profile` in `PendaftaranController::store/update`. Eligibility is validated server-side via `Scholarship::allowsProdi()`/`eligibilityIssueFor()` (prodi must be in beasiswa_prodi snapshot, falling back to campus match when snapshot empty; ipk/semester must meet minimal). Duplicate applications and expired scholarships are rejected. The apply form (user/pendaftaran/buat) shows academic data read-only.

## Sidebar grouping (Stisla dropdown)
`resources/views/layouts/partials/sidebar.blade.php` groups admin menu items into Stisla dropdown submenus (`<li class="dropdown">` + `a.nav-link.has-dropdown` + `ul.dropdown-menu`, toggled by `public/assets/js/scripts.js` `sidebar_dropdown`; parent li gets `active` when any child route is current so the submenu stays open). Admin: "Beasiswa" dropdown (Daftar Beasiswa `admin.beasiswa.*`, Jadwal Pengumuman `admin.pengumuman.*`), "Master Data" dropdown (Kampus `admin.kampus.*`, Pengguna `admin.pengguna.*`), Pendaftar & Template Surat stay single links. User: "Menu Beasiswa" dropdown (Daftar Beasiswa `user.beasiswa.*`, Pendaftaran Saya `user.pendaftaran.*`).

## Demo seed users (database/seeders/UserSeeder.php)
`UserSeeder` (called from `DatabaseSeeder` after `KampusSeeder` + `ScholarshipSeeder`, which is now uncommented) creates 3 active `user`-role demo accounts (`ahmad@sirusa.com`/ahmad, `siti@sirusa.com`/siti, `budi@sirusa.com`/budi, all password `password`) each with a fully-populated `profil_pengguna` (`isProfileComplete()` true: status_orang_tua Lengkap with ayah+ibu data) linked to a real catalog `prodi`, plus one `pendaftar` to the matching seeded beasiswa (ahmad = diterima, siti+budi = verifikasi) so announcement & export pages show sample data. All demo accounts are `status=aktif` and `email_verified_at` set so they can log in immediately.
