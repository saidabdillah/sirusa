# Admin

## Access control = menu grants, NOT role route groups
All route-level `role:*` middleware groups were removed. `routes/web.php` wraps everything after login in `['auth','status.aktif','akses.menu']`. Granting/revoking access is done purely by checking menus on the "Kelola Akses → Akses Menu" page (`Admin\MenuController`), whose matrix is `roles × menus` (pivot `role_menu`); separate from that, the "Kelola Menu" page (`admin.menukelola.*`) adds/edits/deletes the menu entries themselves. Middleware `EnsureMenuAccess` (alias `akses.menu`) 403s any request whose route is covered by a menu that `User::hasMenuAccess()` denies; routes not covered by any menu pass through. `User` model exposes `menus()`, `menuScopes()`, `hasMenuAccess($scope)`, and static `menuScopeCovers($scope, $routeName)` (a menu scope covers its exact route name AND every route prefixed by `scope . '.'`). Views hide/disable action areas with `hasMenuAccess('admin.X.index')`. Default `MenuSeeder` grants:
- `super_admin` = dasbor + everything (beasiswa, pendaftar, all verifikasi menus incl. Kesra's children `admin.kesra.index`/`admin.penerima`/`admin.kesra.disetujui` and the `admin.kesra.status` leaf, kampus, and the whole Kelola Akses group: Role, Pengguna, Akses Menu, Kelola Menu);
- `catpil` = dasbor + `admin.catpil`;
- `kampus` = dasbor + `admin.kampusverif` (NO `admin.kampus` — the Kampus Master Data page belongs to kesra, NOT the kampus role);
- `kesra` = dasbor + `admin.beasiswa` + `admin.pendaftar` + `admin.kesra` (parent dropdown) + `admin.kesra.index` + `admin.penerima` + `admin.kesra.disetujui` (its three children — a child is rendered ONLY when IT is granted, so granting just the parent leaves a dead `<span>`) + `admin.kampus` (Master Data → Kampus is managed by kesra) + `admin.pengguna` — the last one needs its PARENT `kelola-akses` granted too, because `sidebarMenus()` only selects `parent_id` null menus, so without the parent the "Pengguna" item never appears in the sidebar (parents have `scope = null`, so the grant gives visibility only, never route access — look them up by `Str::kebab(label)` in seeders, not by `scope`); child grant keys come from the child's `scope`, which must be UNIQUE (never reuse the parent's scope as a child scope or `keyToId` overwrites the parent's grant key);
- `user` = dasbor + `user.beasiswa` + `user.pendaftaran`.

`MenuSeeder` groups: **Kelola Akses** (section `Administrator`; children Role/`admin.role`, Pengguna/`admin.pengguna`, Akses Menu/`admin.menu`, Kelola Menu/`admin.menukelola`) and **Master Data** (section `Administrasi`; children = Kampus only — Pengguna was moved OUT of Master Data into Kelola Akses).

**Verifikasi section = two leaves + one dropdown + one status leaf (user-approved shape)**: `Catpil` (`fas fa-id-card`, urutan 25, `admin.catpil`) and `Kampus` (`fas fa-graduation-cap`, urutan 26, `admin.kampusverif`) are TOP-LEVEL leaf menus; `Kesra` (`fas fa-clipboard-check`, urutan 27, scope `admin.kesra`, **`route = null`**) is a PARENT dropdown with children `Verifikasi` (route/scope `admin.kesra.index`, urutan 1), `Penerima Beasiswa` (route `admin.penerima.index`, scope `admin.penerima`, urutan 2) and `Keputusan` (route/scope `admin.kesra.disetujui`, urutan 3) — all in section `Verifikasi`, plus the standalone `Status Verifikasi` leaf (route/scope `admin.kesra.status`, section `Administrasi`) for catpil/kampus/kesra/super_admin. `PenerimaBeasiswaController` (`admin.penerima.*`, deliberately NOT prefixed `admin.kesra.` to avoid a scope-prefix collision) lists applicants decided `diterima` with Cetak/Export/Hapus, and its `tarik` action restores one to `verifikasi` (never deletes the row) so it re-enters the decision queue. The child label was renamed `Disetujui` → `Keputusan` (user request; route/scope unchanged, so NO permission change — `buangMenuLama()` prunes the old row on re-seed, but the seeder MUST be run: `php artisan db:seed --class=MenuSeeder`). Kesra became a dropdown on user request; its `route` was removed because a route-less parent renders as an inert `<span>`/`#` dropdown trigger while `scope admin.kesra` keeps covering `admin.kesra.*` for `hasMenuAccess()` and `EnsureMenuAccess` (the dashboard dispatch still counts ONE kesra stage for `hasMenuAccess('admin.kesra.index')` via the parent-scope prefix). The old labels were `Verifikasi Catpil`/`Verifikasi Kampus`/`Verifikasi Kesra`; the "Verifikasi" prefix was dropped because the section header already says it. The old flatten migration `2026_09_25_110300_restructure_verifikasi_menus` was DELETED — do not reintroduce it. Editing shape/labels/grants in `MenuSeeder` REQUIRES running `php artisan db:seed --class=MenuSeeder` on any existing DB (tests seed fresh; dev DBs do not move on their own).

Known ambiguity from that rename: `Kampus` is now BOTH a verification-queue menu (section `Verifikasi`) and a Master Data child (section `Administrasi`). They do not collide in the DB because `updateOrCreate` is keyed on `(section, label, parent_id)`, and the "Akses Menu" matrix disambiguates by printing `({{ $menu->section }})` next to each label — but the "Kelola Menu" delete confirm does NOT, so it reads "Hapus menu 'Kampus'?" for two different menus. Tests that assert sidebar labels must therefore match on `href`/`scope`, not on the label text.

`app/Support/VerifikasiAntrean.php` keeps its own hardcoded "Verifikasi Catpil/Kampus/Kesra" strings, and `DashboardController::actorLabel()` still returns `Catpil`/`Kampus`/`Kesra`. Those are stage/actor names, NOT menu labels, and are deliberately independent of the menu rename — do not "fix" them to match.

There is NO generic `admin` role anymore — always use the specific `catpil`/`kampus`/`kesra`. `dashboard` menu is `wajib` (`RoleController::store` auto-grants it); the grant matrix force-keeps `wajib` menus and, for `super_admin`, also `['admin.role','admin.menu','admin.menukelola','admin.pengguna']` (`MenuController::superAdminModuleIds`).

## Canonical roles (exactly five — short names, NOT `admin_*`)
The `roles` table MUST contain exactly `super_admin`, `catpil`, `kampus`, `kesra`, `user` — created directly with these short names by `DatabaseSeeder`/`seedAkses()`; the historical `2026_09_25` `standardize_roles`/`rename_admin_roles_to_short_names` migrations were DELETED (the app is unpublished: schema changes are edited in-place into the create migrations, never new ALTER TABLE migrations). Treat `catpil`/`kampus`/`kesra` as the ONLY canonical admin role names — never create legacy `admin_*` or old-style short duplicates. The same three strings double as verification STAGE keys (`UserProfile::verifStages()` → `verif_catpil`/`verif_kampus`/`verif_kesra`, `VerifikasiController::STAGES`) — the role/scope/route namespaces `admin.catpil.*`/`admin.kampusverif.*`/`admin.kesra.*` stay unchanged. `DatabaseSeeder`, Pest `seedAkses()`, and `UserFactory` (`admin()`→kesra, `catpil()`→catpil, `kampusAdmin()`→kampus) all seed/assign the short names; keep them in sync (also with `UpdateUserRequest` `in:` whitelist and the peran dropdowns/$roleLabels). `MenuSeeder` writes `role_menu` with `DB::table('role_menu')->insertOrIgnore`, so re-seeding is safe on an existing DB (no duplicate grant rows — `SeederTest` locks this); still run it only when you mean to apply seeder changes.

## super_admin semantic checks that REMAIN (do not remove)
Menu grants cover azimuth; a few hard rules still use `hasRole` because they protect the super_admin account itself:
- `PenggunaController`: the MODULE (index/create/store/edit/update) is gated on `User::canManageUsers()` = `hasMenuAccess('admin.pengguna.index')`, NOT `hasRole` — `MenuSeeder` grants `kelola-akses` + `admin.pengguna` to `kesra`, so superadmin and kesra both manage users out of the box and superadmin can widen it from Akses Menu. `destroy` stays `hasRole('super_admin')` (hapus is the one destructive action kesra must never get), but `toggleStatus` and `resetPassword` use the SAME `canManageUsers()` gate as the module - kesra could already set `status` through the Ubah form (`update()` writes it), so a super_admin-only shortcut was an inconsistency, not a protection. `abortUnlessMayTouch()` (called by `edit()`, `toggleStatus()` and `resetPassword()`) and `UpdateUserRequest::authorize()` (PUT) all 403 a non-super_admin touching a super_admin target. `toggleStatus` also refuses deactivating the actor's own account via `ajaxFail` (redirect + `error` flash), matching `update()`. Destroy blocks deleting self and deleting other super_admins. `resetPassword` (POST `admin.pengguna.reset-password`) sets the account back to password `12345678`.
- `StoreUserRequest`/`UpdateUserRequest` `authorize()` require `canManageUsers()`; `UpdateRoleRequest` + `RoleController::destroy` block touching the `super_admin` role (no manage/delete UI for super_admin).
Views `admin/pengguna/{index,buat,ubah}` conditionally show those actions, and the view gates MUST mirror the controller: Ubah / Nonaktifkan–Aktifkan / Reset Password follow `canManageUsers()` (computed once as `$canEdit`/`$canManageAccount`), while **Hapus User alone follows `$canDelete = hasRole('super_admin')`**. On the Pengguna index the actions live in a dropdown button-group (the "Ubah Role" label is just **Ubah**), each backed by its own form and per-page `@push('script')` Swal confirm handler (`.btn-confirm-toggle` for toggle+reset, `.btn-delete` for hapus). The `admin/pengguna/ubah` form contains NO email display and NO password fields — password changes are NOT possible there (only the index's Reset Password quick action resets to `12345678`). The super_admin row has no action buttons at all. TESTING GOTCHA: do not assert the delete form is absent with `assertDontSee(route('admin.pengguna.hapus', $user))` — the delete URL `/admin/pengguna/{id}` is a PREFIX of the ubah and status URLs, so that assertion always fails. Assert on `Hapus User` and `value="DELETE"` instead; `btn-delete` also appears in the page's closing JS comment.

## User management identity rules (create/edit)
`peran` in BOTH requests is `required` + `Rule::in($this->user()->assignableRoles())` — see `.ai/rules/user.md` for why it is neither `Rule::exists('roles','name')` nor `nullable`. `username` uses `required_unless:peran,user` (required for non-user peran, unique) but auto-generated (`usr` + Str::random(8)) for `user` peran. Do NOT write `required_if:peran,!user` — Laravel does not support `!` negation in string dependent rules (it only matches the literal string `!user`), use `required_unless` instead (error message tasks ask for "Username wajib diisi untuk akun non-mahasiswa"). `email` is nullable/OPTIONAL (the buat form shows NO `*` on Email); `password`+`password_confirmation` required unless peran = user (initial password = `12345678`); `nik` `required_if:peran,user` ONLY (non-user roles submit no NIK — `required_unless:peran,super_admin` was a bug that forced NIK on every staff account), unique on `profil_pengguna`; there is NO `nim` rule (mahasiswa set it on the Profil page); `kampus_id` uses `Rule::requiredIf($this->input('peran') === 'kampus')` (the label carries `*`) + `exists:kampus,id`. `PenggunaController::store` sets password to `12345678` when peran = user and seeds `profile()->create(['nik' => $validated['nik']])`, and its success flash mentions the initial password only for the mahasiswa branch. `UpdateUserRequest` applies the SAME `kampus_id` `Rule::requiredIf(peran === 'kampus')`. It has NO `password`, `nik`, or `nim` rules — the edit ("Ubah") form only changes peran and status (username/email/password/NIK/NIM are fixed after creation); password resets go through the dedicated `admin.pengguna.reset-password` action only. `PenggunaController::update` updates only `status`/`kampus_id` explicitly and calls `syncRoles($validated['peran'])` — never pass `peran` to `update()`, it is not fillable.

## Pengguna create/edit views toggle field blocks by peran
`admin/pengguna/buat` shows/hides three blocks via a jQuery `toggleAkun()` on `#peran` change: `#akunMahasiswa` (NIK, visible only for peran `user` — note the staff password block is `#akunStaf` and must show when NOT user: the old vanilla-JS version had `akunStaf.classList.toggle('d-none', !isUser)` which INVERTED it so password fields appeared for mahasiswa and vanished for admins), `#akunStaf` (Kata Sandi + Konfirmasi, hidden for peran `user`), `#akunKampus` (kampus select, only peran `kampus`), and the username field wrapper `[data-field="username"]` (hidden for peran `user` — auto-generated). `admin/pengguna/ubah` renders ONLY Username (readonly), Peran (`old('peran', $user->roles->first()?->name)` fallback — no preselected default), Status, and the `#akunKampus` select; NO NIK inputs and NO password fields (test asserts `assertDontSee('name="nik"')` and `Konfirmasi Kata Sandi`); email/NIK show as read-only text in the right-hand Informasi card.

## Beasiswa, kampus, pendaftar: single admin group
There is no super_admin/admin role split for scholarship, kampus, or pendaftar routes anymore — access follows the menu grant (`admin.beasiswa`, `admin.kampus`, `admin.pendaftar`). Form Requests for those modules `authorize()` with `return true;` — the `akses.menu` middleware is the only guard. Buttons in `admin/beasiswa/{index,lihat}`, `admin/kampus/*`, `admin/pendaftar/index` gate on `hasMenuAccess('admin.beasiswa.index'|'admin.kampus.index'|'admin.pendaftar.index')`. Since super_admin and kesra are granted everything by default, both CAN manage beasiswa/pendaftar (intended; the old "super_admin is view-only" rule is obsolete).

## Scholarship form uses the local kampus catalog
The admin beasiswa create/edit form selects one `kampus_id` from the local `kampus` table (checkbox tree of catalog fakultas→prodi posting `prodi_ids[]`). Store/UpdateScholarshipRequest validate `kampus_id` + `prodi_ids` and use `after()` to reject prodi whose fakultas.kampus_id != selected kampus. Store/update resolve the kampus name into the legacy `beasiswa.kampus` text column and rebuild snapshot rows via `syncFakultas()`. Only store() creates the pendaftaran row; there is no announcement/notification send anywhere. Tables `kampus→fakultas→prodi` live in migration `2026_08_24_000001_create_kampus_table.php` (edited in place; project runs `migrate:fresh --seed`, do NOT create new migration files). The scholarship form has NO "Tunjangan" (`cakupan`) field and uses two flatpickr date inputs `tanggal_mulai`/`tanggal_selesai` instead of the old single `batas_waktu` (see `views.md` → "Beasiswa periode & UKT cleave").

## Form Tambah Menu harus mulai bersih; form Ubah tidak boleh ikut berubah
Setiap modal adalah instance Blade tersendiri, jadi nilai `old()` TIDAK bisa bocor antar-modal — yang bocor hanya *state visual error*. Tiga aturan yang menjaga ini:

- **`<select>` Section di `modal-tambah` wajib punya `<option value="">` (placeholder `— Pilih —`).** Tanpa opsi kosong, browser diam-diam memilih opsi pertama, yaitu `"Menu Utama"`, dan user.submit form itu tanpa pernah menyentuhnya. `modal-ubah` sengaja TIDAK memakai opsi kosong karena `section` wajib diisi dan nilainya selalu tersimpan.
- **Error residue dibersihkan di `hidden.bs.modal`, bukan `show.bs.modal`.** Ada jalur fallback di `kelola.blade.php` yang membuka ulang modal setelah page reload dengan error yang sudah dirender server; membersihkannya saat `show` akan menghapus error itu sebelum sempat dibaca. Pada page load baru modal belum pernah dibuka, jadi `hidden` tidak pernah menyala dan error render-server tetap utuh. Selektor `.invalid-feedback`-nya juga harus tanpa `[data-ajax]`, karena blok `@error` merender `invalid-feedback d-block` — `d-block` yang memaksa pesannya tetap terlihat walau `is-invalid` sudah dicabut, jadi kalau hanya blok AJAX yang dibersihkan, membuka ulang modal akan meninggalkan pesan tanpa border merah.
- **Pembersihan itu HANYA state visual (`is-invalid`, `aria-invalid`, `invalid-feedback[data-ajax]`).** Jangan pernah ikut menyimpan/mengembalikan `.val()` di handler itu — form Ubah akan mengosongkan dirinya sendiri setiap kali dibuka.

## Profile verification stages (catpil + kampus parallel, then kesra)
`Admin\VerifikasiController` drives profil verification. Routes `admin.catpil.*`, `admin.kampusverif.*`, `admin.kesra.*` use `->defaults('stage', ...)` and a bound `{user}`. CRITICAL dispatcher gotcha: Laravel aligns controller params POSITIONALLY against `array_values($route->parameters())`, which orders the bound `{user}` model before the `stage` default — so method signatures MUST be `(User $user, string $stage, ...)` (User first, then stage, then FormRequest). Stage order and mapping live in `UserProfile::verifStages()` (`catpil/kampus/kesra` → `verif_*`/`catatan_*` columns).

**There are NO inter-stage prerequisites anymore.** Catpil and Kampus run in PARALEL the moment the profile is complete: `canVerifStage()` is the WRITE gate — `'catpil' => true`, `'kampus' => verif_kesra !== 'setuju' && profile->user has an applicant row`, `'kesra' => verif_catpil === 'setuju' && verif_kampus === 'setuju'`. Queue VISIBILITY is a separate predicate, `UserProfile::inVerifQueue($stage)`: same as `canVerifStage()` except kampus returns true whenever the user has an applicant row, so a Kesra-decided (locked) kampus row stays in the queue read-only. Keep the two split — `VerifikasiAntrean::antrean()`, its `ringkasan()` counts and the kampus export all use `inVerifQueue()`, while `verifikasi()` (PUT) still uses `canVerifStage()` so writes 403 when locked. `resetDownstreamStages()` was DELETED — `verifikasi()` writes only its own stage's two columns, so a revisi/tolak in one stage never erases the other stage's work. The same removal unlocked registration: `PendaftaranController::profilError(User $user)` gates ONLY on `isProfileComplete()` (the `?UserProfile $profile` + Catpil-approved parameter is gone), and `User\BeasiswaController::show` no longer computes `$catpilVerified` (the `@elseif(! $catpilVerified)` block in `user/beasiswa/lihat` was deleted) — a student registers as soon as their profile is complete, and the data still auto-enters the Catpil queue. `UserProfile::isCatpilVerified()` was deleted with it; never reintroduce a "verified first" gate.

**Kampus locks READ-ONLY once Kesra decides, and that is the accepted trade-off.** The Kampus row STAYS in the queue as soon as `verif_kesra === 'setuju'` (set by `KeputusanPendaftaranController::update()` on ANY Kesra decision — accepting OR rejecting — deliberate: user-approved lock key), but the action cell switches to a muted read-only **Lihat** link (`btn-outline-secondary` + `fa-eye`) instead of the Verifikasi/Ubah Keputusan button, and the detail page opens read-only with a locked alert (no form, no `@push('script')`). Queue visibility comes from `UserProfile::inVerifQueue()` (does NOT drop the row); the write gate `canVerifStage()` still returns false, so PUT/`verifikasi()` answers 403. Do not "fix" this back to hiding the row. Unlock paths: Kesra's Hapus action, a revised Kesra decision, or a profile edit (`resetVerification()`). `verifikasi` action sets `{$verif}=status` + `{$catatan}=catatan` and redirects to the stage index. Keputusan is `setuju|revisi|tolak` (see `VerifikasiProfilRequest`, which still accepts `menunggu` server-side even though the view no longer offers Tarik Kembali). `UserProfile::verifStatus()` returns `revisi` if any stage is `revisi`, else `tolak` if any is `tolak`, else `proses`. Index queries `User::role('user')->where('status','aktif')` filtered by `UserProfile::inVerifQueue`. Profile save (ProfileController) calls `resetVerification()` which resets all stages to `menunggu` and clears catatan — the profile must be re-verified after any edit.

## Roles & menus management
`Admin\RoleController`: index lists roles WITHOUT user-count/menu-count columns; store/create auto-grants `wajib` menus; update; destroy refuses `super_admin` and any role still holding users. There are NO `create`/`edit` page methods — Tambah/Ubah run through modals on the index page (routes `admin.role.simpan`/`perbarui` only; `role.buat`/`role.ubah` GET routes no longer exist). `Admin\MenuController` splits into TWO areas:
- **Akses Menu** (`/menu`, scope `admin.menu`) is a PER-ROLE assignment screen, not a roles×menus matrix: `index(Request)` reads `?role=` with NO default (the filter starts empty with a `-- Pilih Role --` placeholder and the checklist only renders once a role is picked; there is no super_admin fallback), and passes `$roles`/`$roleLabels` (= `User::ROLE_LABELS`)/`$activeRole`/`$menus`/`$grants` (only that role's `role_menu` ids) + `$lockedMenuIds` (wajib menus, plus super_admin module-scope menus when the active role is `super_admin`). The view renders a GET role filter (`<select name="role" id="roleFilter">` + Cari/Reset, same style as the pendaftar/verifikasi filters) and a single `table-striped` TABLE in ONE tbody (kelola-menu style): each section opens with a NON-collapsible `table-active` header row carrying an inline "Pilih semua" `[data-section-toggle]` checkbox (rows keep `[data-section-body="{i}"]` purely to scope the per-section toggle), then parent rows and `table-light` `pl-5` child rows; there is NO search box, NO collapse chevron, and NO "otomatis" badge (locked rows are just `checked disabled`). `@push('script')` JS auto-checks a parent when a child is checked and cascades parent→children (locked/disabled boxes are skipped). `perbarui` (PUT `/menu`, route name `admin.menu.grants` — the only alias under `admin.menu` besides `index`) now takes `role_id` + `menus[]`, syncs ONLY that role's `role_menu` inside a DB transaction (saving one role NEVER wipes another — fixes the old matrix bug), force-adds `wajib` menus, and force-keeps `self::SUPER_ADMIN_MODULE_SCOPES` (`['admin.role','admin.menu','admin.menukelola','admin.pengguna']`) on super_admin. `UpdateMenuAccessRequest` validates `role_id` (required, exists) + `menus[]` (exists), NOT the old `grants` array.
- **Kelola Menu** (`/menu/kelola`, scope **`admin.menukelola`**, routes `admin.menukelola.index/simpan/perbarui/hapus` — NO `buat`/`ubah` GET routes): the index renders the tree list and all add/edit happen via Bootstrap MODALS (partials `admin.menu.modal-tambah` + per-menu `admin.menu.modal-ubah`; `kelola()` passes `$menus`, `$parents` (top-level for the parent select), `$sections`). THE MODALS MUST BE RENDERED AT `<body>` LEVEL, NOT inside `.main-content`/`.main-wrapper`: those ancestors form a stacking context so `position:fixed` modals land UNDER the backdrop (symptom: "modal seperti di belakang"). Pattern: pages emit them inside `@push('modal')`, the layout outputs `@stack('modal')` right before `</body>` (after `@stack('script')`); variable scope stays intact because `@push` blocks evaluate where they're written, still inside `@section('content')`. Naming gotcha — these routes MUST NOT be prefixed `admin.menu.`, because `menuScopeCovers('admin.menu', $routeName)` covers every `admin.menu.*` route; the `admin.menukelola.*` namespace avoids the prefix collision. Modal forms carry a hidden `modal_target` (e.g. `modal-tambah-menu`, `modal-ubah-menu-{id}`) and on validation failure redirect back to the index where JS reopens `old('modal_target')` with `$('#id').modal('show')`; every `old()`/`$errors` render in a modal is gated by `$isTarget = old('modal_target') === <that modal's id>` so a failed submit only re-fills/reopens the modal that was submitted. `store` auto-grants the new menu to `super_admin`; `destroy` refuses `wajib` menus and menus that still have children. `Menu::sections()` is DYNAMIC: `DEFAULT_SECTIONS` union every distinct `menus.section` in the DB (ordered by `urutan`, then `label`, no static cache) - an unknown section renders, it is no longer an allow-list. Both modal forms expose SEVEN fields - `label`, `parent_id`, `icon`, `section`, `urutan` (route/scope route/scope **OPSIONAL**, boleh diisi/dikosongkan di form, filled by the developer via `MenuSeeder`/`tinker`; see `menu.md`. `validated()` never carries them, so posted route/scope is ignored and the columns stay NULL until coded). Any leaf without a registered route still renders as a clickable `<a>` (see `Menu::linkUrl()`), pointing at a URL that yields 404; `aktif`/`wajib` inputs stay GONE and no `<small>` hint texts sit under any input. `aktif`/`wajib` rules were dropped from BOTH requests, so `store()` forces `aktif => true, wajib => false` and `update()` uses plain `$menu->update($validated)` which never touches those two columns. Required fields (Label Menu/Section/Urutan) carry a VISUAL `<span class="text-danger">*</span>` in both modals, and HTML `required` attributes stay forbidden. Update rejects `parent_id` equal to the menu's own id. `parent_id` is `nullable|string|max:100` plus `Rule::when(fn (Fluent $data) => ! Menu::isExistingMenuId($data->parent_id ?? null), ['min:2'])` (no numeric rule on the attribute, so `min` measures STRING length of an unknown label), and `prepareForValidation()` trims `parent_id`/`label`/`section` in both requests.

**Inline parent/section creation (`MenuController::resolveParentId`)** - the two selects are Select2 `tags`, so `parent_id` arrives as either an existing menu id, an empty string, or a typed label. The resolver runs ONLY when `array_key_exists('parent_id', $request->all())` (a programmatic PUT without the key must not reparent), and: empty -> null (top-level); a digit string that `Menu::isExistingMenuId()` finds -> `(int)`; otherwise a case-insensitive match against `parent_id IS NULL` rows (retype of an existing group reuses that row - locked by a test using `bEaSiSwA`) or a new TOP-LEVEL menu is created with `route`/`scope` null, `icon = fas fa-folder`, `section` + `urutan` inherited from the child being saved (so the new group appears in the same section/position as its first child), `aktif` true, `wajib` false, then `grantToSuperAdmin()` inserts the `role_menu` row via `DB::table('role_menu')->insertOrIgnore`. Only `parent_id IS NULL` rows are matched/created (the sidebar renders two levels; a deeper parent would be invisible). `section` accepts any non-empty string (`Rule::in` was removed) - a brand-new section works immediately because `Menu::sections()` is dynamic. All routes under `admin.menu` and `admin.menukelola` are granted only to `super_admin`, so non-super_admins get 403.

## Admin list views use server-side DataTables
Kampus (kampus/fakultas/prodi), beasiswa, and pendaftar index pages are server-side DataTables (Stisla `datatables.min.js`): the tbody is still hydrated inline (so existing `KampusManagementTest`/`PendaftarFilterTest` keep passing) and each table re-requests its JSON endpoint via `ajax: { url: route('admin.X.data') }` with `serverSide: true`. One GET endpoint per table lives in the controller (`data(Request)`), behind a `admin.X.data` route registered inside the same menu-gated group (covered → 403 by `EnsureMenuAccess`). All JSON is produced by `App\Support\DataTablesProcessor`: ctor `(Request $request, Builder|Relation $query, array $config, Closure $rowBuilder)`. `$config` keys: `searchable` (strings or `fn($q,$term)=>` closure, run inside one `where(...)` group), `orderable` (`columnIndex => dbCol`), and optional `filter` (`fn(Builder $query, Request $request)`) executed AFTER `recordsTotal` but BEFORE `recordsFiltered` — NEVER pre-filter the query in the controller before constructing the processor or `recordsTotal` will reflect the filter. Row cells are built in PHP, single-sourced through the same `_aksi` partial the inline tbody uses; `aksi`/`checkbox` cells are gated by `hasMenuAccess('admin.X.index')` so empty rows stay column-complete. EXCEPTION: the **pendaftar** table is fully READ-ONLY — it has no aksi/checkbox cell at all (its old `_aksi` partial and `admin.pendaftar.lihat` route were deleted; `data()` returns no `aksi` key and the DataTable `columns`/`columnDefs` end at the `status` column, target `[0]`). Index pages keep a `->limit(25)->get()` tbody (first page) while `data()` serves full pagination (length `-1` capped at 100). Do not add Tailwind/Bootstrap 5 — STISLA + Bootstrap 4 only. The pendaftar index filter (`status` + `beasiswa_id`) submits via a GET "Cari" button (`type="submit"`), NOT `onchange="this.form.submit()"` — the selects must never auto-submit; keep a separate Reset link.

## Sidebar (Stisla) is dynamic
`resources/views/layouts/partials/sidebar.blade.php` renders sections in order from `Menu::sections()` (`['Menu Utama','Administrasi','Verifikasi','Administrator','Layanan Mahasiswa','Pengaturan','Manajemen']`). Section labels must describe the group's function — the old `'Menu Admin'`/`'Menu Pengguna'` pair said nothing about what the group contained and was replaced. `section` is a plain string, not a foreign key: renaming one in `sections()` does NOT migrate existing `menus.section` rows, only `MenuSeeder` (idempotent `updateOrCreate` keyed on `(section, label, parent_id)` + `buangMenuLama()`) moves them. **`sections()` is NO LONGER an allow-list** - it returns `DEFAULT_SECTIONS` ∪ whatever `menus.section` values exist in the DB, so a menu in an unlisted section renders under its own (sorted) header instead of vanishing. What still needs `php artisan db:seed` is MOVING a menu between sections: `updateOrCreate` is keyed on `(section, label, parent_id)`, so the row stays in the old section until `buangMenuLama()` prunes it, and `Menu::sections()`'s `urutan` ordering for the new header comes from the menu rows themselves.

Section membership is display grouping ONLY: it does not grant or revoke access. Access stays with the `role_menu` grant matrix, and `User::sidebarMenus()` does not filter by `section` at all — it only filters `parent_id` null + `aktif` + granted. A section header is rendered only when the user has at least one menu in it, so a restricted role never sees an empty header. Note `super_admin` is NOT granted `beasiswa-saya`, so its sidebar has four sections and no "Layanan Mahasiswa" — that is pre-existing and correct. It iterates `$user->sidebarMenus()` — a `User` helper returning ONLY top-level menus (`whereNull('parent_id')`, `aktif`, granted to the role) with already-filtered ordered `children` (granted + `aktif`, sorted by `urutan`). Do NOT switch back to `$user->menus()`: it returns every granted menu including children, and rendering children as top-level items was the old "double menu" sidebar bug. Leaf links call `route($menu->route)` guarded by `\Illuminate\Support\Facades\Route::has($menu->route)` — an unregistered/stale route renders a dead `<span>` instead of crashing (submit zero-length menu pages). Parent dropdowns render only when `children` is non-empty. Parent `li` gets `active` when any granted child route is current so the submenu stays open.

## Pengguna module: menu grant for breadth, hasRole only to guard super_admin AND delete
Index/create/store/edit/update are gated on `User::canManageUsers()` (= `hasMenuAccess('admin.pengguna.index')`), so the Akses Menu matrix — not a hardcoded role list — decides who may open the module; `MenuSeeder` grants `kelola-akses` + `admin.pengguna` to kesra (the parent grant is what makes the item appear in the sidebar, since `sidebarMenus()` only selects `parent_id` null menus). **`toggleStatus()` and `resetPassword()` are ALSO gated on `canManageUsers()`**, not `hasRole('super_admin')`: kesra could already change `status` through the Ubah form (`update()` writes `status`), so keeping the shortcut super_admin-only only meant the two paths disagreed. **`destroy()` alone stays `hasRole('super_admin')`** — hapus is the one destructive action kesra must never get; ubah / ubah status / reset password are hers. `abortUnlessMayTouch()` / `UpdateUserRequest::authorize()` 403 any non-super_admin touching a super_admin target, and `toggleStatus()`/`resetPassword()` now call `abortUnlessMayTouch()` too, so the GET form, the PUT, the PATCH and the reset POST all fail the same way.

## update() and toggleStatus() guard the actor's own account and super_admin targets
`update()` returns a redirect + `error` flash (never an exception) when the actor changes their own `peran` or sets their own `status` to `non-aktif`, and when a `super_admin` target's `peran` is changed or its `status` is set to `non-aktif` — the form was previously able to demote and deactivate super_admins, which `destroy()`/`toggleStatus()` already refused. `toggleStatus()` repeats the own-account guard on the PATCH path (returns `ajaxFail` with an `error` flash, not an exception) because the Ubah form was never the only way in: the list shortcut used to let a super_admin disable themselves, and widening the gate to kesra would have widened that hole. It also calls `abortUnlessMayTouch()` so a kesra POST cannot toggle a `super_admin` row — the earlier `if ($user->hasRole('super_admin'))` branch that returned `ajaxFail` is gone, because the 403 now happens before the target is inspected.

## Kesra "Disetujui" page and the Hapus that resets one approval
`KeputusanPendaftaranController::disetujui()` renders `admin/verifikasi/kesra-disetujui.blade.php`: the archive of `pendaftar` rows with `status = 'diterima'`, fed by `VerifikasiAntrean('kesra')->pendaftaran('diterima')` (route `admin.kesra.disetujui`, GET `/verifikasi/kesra/disetujui` — MUST be registered BEFORE `/verifikasi/kesra/{user}` or the segment gets caught by model binding and 404s). There is NO header button to this page on `kesra.blade.php` anymore (removed with the "Antrean Putusan" button on the archive page — user request): entry is the sidebar dropdown child, and the header of both pages carries only "Unduh Excel" on the archive side. `batalkan()` (DELETE `admin.kesra.pendaftaran.hapus`, `/verifikasi/kesra/{user}/pendaftaran/{applicant}`) is the ONLY reset path and it never deletes a row: inside a transaction it sets `status = 'verifikasi'` (re-opens the Kesra queue and frees the quota slot, since quota counts `status='diterima'`), clears `catatan`/`diputuskan_at`/`diputuskan_oleh`, then RECOMPUTES `verif_kesra`: it stays `'setuju'` while ANOTHER row of the same user still holds `diterima`/`ditolak`, otherwise it goes back to `'menunggu'`. Only `diterima` rows are accepted (`ajaxFail` otherwise — `ditolak` rows are edited through the normal decision form, so Hapus must not become a second write path for them), `$applicant->user_id` mismatch 404s, and both methods guard `hasMenuAccess('admin.kesra.index')` like `update()` does. Hapus is also what unlocks the Kampus stage again.

## One Kesra decision, written to both the applicant row and verif_kesra
Kesra has exactly one decision per registration. `update()` writes `pendaftar.status` AND sets `verif_kesra='setuju'` in the same transaction, inside the existing `lockForUpdate()` quota block (which excludes the applicant itself, so revising an accepted row is not blocked by its own slot). The profile-level endpoint `admin.kesra.verifikasi` is 403 for stage kesra — do not reintroduce a form or gate that requires `verif_kesra='setuju'` first. `pendaftar_status` accepts only `diterima`/`ditolak`; there is no pull-back to `verifikasi` from that form (the Hapus action above is the pull-back).

## Filter "semua status" pakai sentinel, bukan string kosong
Middleware `web` sudah termasuk `ConvertEmptyStringsToNull`, jadi `?filter=` sampai ke controller sebagai `null` — sama persis dengan tidak mengirim `filter` sama sekali. Karena itu "tampilkan semua status" memakai nilai sentinel `Applicant::FILTER_ALL` = `'semua'`, bukan `value=""` di select. Tanpa filter (null) = antrean yang menunggu; `semua`/nilai tak dikenal = semua status. Kalau suatu saat filter kosong perlu berarti "semua", sentinel ini yang harus diubah, bukan select-nya.

## Kampus lock key is verif_kesra = setuju; row stays read-only; Hapus recomputes it
The Kampus row STAYS visible in the queue but becomes read-only (action → muted **Lihat** link; detail page read-only with locked alert) as soon as `verif_kesra === 'setuju'`, which Kesra's `update()` writes on ANY decision — accept OR reject. This locks Kampus after a rejection too; the user explicitly approved that trade-off. Unlock paths only: Kesra Hapus, a revised Kesra decision, or profile edit (resetVerification).

Hapus (`KeputusanPendaftaranController::batalkan`, DELETE admin.kesra.pendaftaran.hapus) accepts only `diterima` rows and never deletes the row: status → 'verifikasi', clear catatan/diputuskan_at/diputuskan_oleh, then recompute verif_kesra — keep 'setuju' while another row of the same user still holds diterima/ditolak, else 'menunggu'.
