## Input file profil memakai custom-file (gaya KRS/KHS), bukan input-group
Semua input file di `profil/index.blade.php` (11 dokumen + prestasi) memakai pola `custom-file` Bootstrap: `custom-file-input` + `custom-file-label` (permintaan pengguna) — BUKAN `input-group` + tombol mata. Nama berkas TERPILIH ditampilkan handler `.custom-file-input` change (multi-file: "N berkas dipilih"); label render awal menampilkan `basename()` berkas tersimpan, dan tautan "Lihat berkas tersimpan" menggantikan tombol mata. Validasi KRS/KHS: struktur longgar di `rules()`, kewajibannya PER-BARIS di `withValidator()` — baris KRS yang DIKIRIM wajib berisi BERKAS, baris KHS yang DIKIRIM wajib berisi NILAI (berkas boleh menyusul), kecuali baris itu sudah tersimpan (simpan-ulang tanpa unggah-ulang tetap sah); pesannya menyebut jenis+semester ("Berkas KRS semester 3 wajib diunggah.", "Nilai KHS semester 3 wajib diisi."). `profile()` mengembalikan RELASI HasOne — panggil `->first()` sebelum `dokumenAkademik()`. JANGAN kembali ke `dokumen_akademik => required|array` global: itu menolak profil tanpa baris akademik sama sekali (sudah pernah terjadi).

## KRS/KHS dirender sebagai SATU TABEL per semester
`profil/partials/dokumen-akademik-tabel.blade.php` (dipakai `profil/index.blade.php`) merender satu `<tr>` per semester dengan kolom Semester, Berkas KRS, Berkas KHS, Nilai KHS — bukan blok dua kolom per semester. Alasan: semester 8 dulu menghasilkan 16 blok dan halaman sangat panjang (permintaan pengguna, "agar tidak banyak scroll"). Berkas tersimpan tampil sebagai nama berkas di label + tombol ikon mata, supaya tinggi baris tidak ikut nama berkas panjang. CSS-nya (`#tabel-akademik` di `custom.css`) mengecilkan `custom-file` agar muat satu baris. `profil/partials/dokumen-akademik.blade.php` adalah versi KARTU lama yang disimpan sementara sebagai pembanding — hapus kalau Said sudah memilih tabel.

`dokumen-akademik-kartu.blade.php` juga ada sebagai pembanding bentuk kartu; jangan dipakai produksi kecuali Said memintanya.

Batasan baris: KRS sampai semester aktif, KHS sampai semester aktif dikurangi satu (KHS semester berjalan belum terbit). `tampilkanBarisAkademik()` menghitungnya PER JENIS di dalam satu baris tabel, lalu memanggil `aturInput($input, tampil)`. Baris yang sudah DIISI tetap terkirim walau di luar batas (isian user tidak hilang diam-diam saat semester diubah).

## KRS hanya berkas; NILAI hanya milik KHS
KRS adalah rencana studi (daftar mata kuliah) dan tidak memuat nilai, jadi baris KRS di `partials/dokumen-akademik` hanya punya input BERKAS — tidak ada input/label "Nilai KRS Semester N" (permintaan pengguna). Konsekuensinya berantai dan harus konsisten di empat tempat: (1) rule nilai di `UpdateProfilRequest` memakai kunci `dokumen_akademik.khs.*.nilai`, bukan `*.*.nilai`, jadi nilai yang dikirim pada baris KRS tidak divalidasi; (2) `withValidator()` hanya menghitung `adaNilai` untuk KHS, jadi baris KRS tanpa berkas tetap ditolak walau ada angka nilai; (3) `ProfileController::simpanDokumenAkademik()` men-null-kan `$nilai` untuk jenis selain KHS, jadi angka itu tidak pernah tersimpan; (4) `partials/profil-detail` hanya menampilkan "Nilai:" untuk baris KHS. Kolom `dokumen_akademik.nilai` TETAP ada di database (dipakai KHS) — jangan dihapus. Locked by ProfilAkademikTest 'baris KRS hanya berisi unggah berkas, nilai hanya ada di baris KHS', 'nilai yang dikirim pada baris KRS diabaikan, bukan disimpan', 'baris KRS tanpa berkas ditolak walau ada nilai'.

## Baris KRS/KHS mengikuti SEMESTER AKTIF: KRS sampai semester itu, KHS sampai semester sebelumnya
`tampilkanBarisAkademik()` di `profil/index.blade.php` membaca SEMESTER yang dipilih (bukan hanya jenjang): baris KRS dirender sampai semester aktif, baris KHS sampai semester aktif DIKURANGI SATU — mahasiswa semester 2 memegang KRS semester 2 (rencana studi berjalan) dan KHS semester 1 (KHS semester berjalan baru terbit setelah semester selesai; permintaan pengguna). Baris di luar batas di-toggle hidden + disabled (input nonaktif tidak terkirim; backend tetap memvalidasi semester di luar jenjang lewat `withValidator`). Baris yang sudah DIISI (berkas dipilih atau nilai diketik) TIDAK ikut dinonaktifkan walau tersembunyi — kalau ikut, isian itu hilang diam-diam saat user mengubah semester sebelum menekan Simpan, dan user mengira barisnya "bertambah kosong". Baris yang sudah TERSIMPAN tidak terpengaruh (berkasnya di disk, path di database); yang muncul sebagai baris kosong baru adalah semester di atas batas lama, dan itu memang wajib diisi (`withValidator`). Tanpa semester terpilih, SEMUA baris KRS/KHS nonaktif. Listener `#semester` change ikut memanggil fungsi itu, dan jenjang yang berganti mengosongkan semester lalu menyembunyikan semua baris. Petunjuk dinamis `#petunjuk-akademik` (di `partials/dokumen-akademik`) menjelaskan batasnya dengan angka. Aturan backend TIDAK berubah: unggah semester mana pun tetap diterima server (form bukan penjaga). Locked by ProfilAkademikTest 'baris KRS dan KHS mengikuti semester aktif yang dipilih'.

## Status kepala keluarga adalah OPSI KEEMPAT pada radio Ikut KK, bukan input terpisah
`ikut_kk` berkempat nilai: `ayah`, `ibu`, `famili_lain`, `kepala_keluarga` (permintaan pengguna Oct-2026). Kolom boolean `kepala_keluarga` TETAP ada di database tapi bukan input mahasiswa: `UpdateProfilRequest::prepareForValidation()` SELALU menimpanya dari pilihan radio (`kepala_keluarga` = opsi `kepala_keluarga` dipilih), jadi payload manual tidak bisa menyelundupkan nilai berlawanan; rule `kepala_keluarga => required|boolean` tetap ADA supaya nilai hasil hitungan ikut `validated()` dan tersimpan. Enum di migrasi `2026_08_25_000002_create_profil_pengguna_table` (pemilik kolom) memuat keempatnya. Indikator read-only "Ikut KK" di `partials/profil-detail` juga memuat opsi keempat. Data ayah dan ibu tetap wajib diisi." — data ayah/ibu TETAP wajib walau mahasiswa kepala keluarga; hanya blok wali yang bergantung `famili_lain`. Tidak ada `kepala_keluarga_display` lagi di form. Locked by ProfilAkademikTest 'status kepala keluarga adalah opsi keempat pada radio Ikut KK' + 'memilih Kepala Keluarga pada Ikut KK menyimpan boolean kepala_keluarga'.

## Only role `user` (mahasiswa) has a profile; staff accounts get account info only
`PenggunaController::store()` only creates a `profil_pengguna` row for `peran = user`, so super_admin/kesra/kampus/catpil have NO profile at all. The profil page therefore gates the entire form, all completeness/verification alerts, the document upload groups and the whole `@push('script')` (Cleave, flatpickr, campus cascade, wali toggle) behind `User::isMahasiswa()` (`hasRole('user')`), leaving staff with only the "Informasi Akun" card (`col-12 col-lg-6`, row `justify-content-start`, NOT `offset-lg-3`) that points at `settings` for email/password.

The "Informasi Akun" card is for STAFF ONLY: mahasiswa must not see it at all (permintaan pengguna Oct-2026 — username/role/tanggal terdaftar bukan informasi yang bisa ia pakai di halaman profil; email sudah jadi field form, kata sandi ada di Pengaturan). Consequently the mahasiswa form card spans the full width (`col-12`, not `col-lg-8`) because there is no second card beside it; the row keeps no alignment class (`<div class="row ">`). Locked by ProfilStafTest: 'halaman profil akun staf hanya menampilkan informasi akun', 'mahasiswa tetap melihat form profil lengkap dengan unggah berkas' (asserts `assertDontSee('Informasi Akun')` and `not->toContain('col-lg-8')`), 'row profil mahasiswa tidak dipaksa perataan tertentu'.

`ProfileController@index` also skips `WilayahService::getDistricts()` (an outbound HTTP call) and the `Kampus::with('fakultas.prodi')` query for staff. The guard is server-side too: `UpdateProfilRequest::authorize()` returns `$this->user()->isMahasiswa()` so a hand-crafted PUT gets 403 — hiding the form in the UI is not a boundary (see views.md).
